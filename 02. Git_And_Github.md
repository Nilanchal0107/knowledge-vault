## 1. What is Git?

Git is a **Version Control System (VCS)** — software that tracks changes in your files over time.

Think of it like **checkpoints in a video game**:
- You save your progress at certain points
- If something goes wrong, you can go back to a previous checkpoint
- Git does the same for your code

### Why Git?
- Free and Open Source
- Works with any programming language (C++, Java, Python, JavaScript, PHP…)
- Tracks every change ever made to your codebase
- Enables collaboration — multiple people can work on the same project without interfering with each other

### Before Git
- **SCCS** — proprietary, expensive
- **CVS**, **SVN (Subversion)**, **Perforce**, **Mercurial** — all similar tools, some paid
- Git changed everything: free, fast, distributed, and now industry standard

## 2. Git vs GitHub

| Git | GitHub |
|-----|--------|
| A **software** (VCS) installed on your machine | An **online service** that hosts Git repositories |
| Works locally | Works on the cloud |
| Free & Open Source | Free (with paid tiers) |
| Core tool — always needed | Optional but widely used |

> **Key Rule:** Never confuse Git and GitHub.  
> Git = the core software. GitHub = one of many online hosting services.

### Other Git Hosting Services
- **GitLab**
- **Bitbucket**
- **Azure Repos**
- **Gitea**
- **GitHub Enterprise** (self-hosted)

Many large companies host their own Git servers internally for security reasons.

## 3. Setup & Installation

### Install Git
Download from: [git-scm.com](https://git-scm.com)

```bash
# Check installed version
git --version
```

> Git is extremely stable. Breaking changes almost never happen. What you learn today will work 3–5 years from now.

### Recommended Terminal
- **Windows:** Use **Git Bash** (comes with Git installation) — supports Linux commands like `ls`
- **Mac:** Use Terminal or [Warp](https://www.warp.dev/)
- **Code Editor:** VS Code (recommended)

### Configure Git (Global)

```bash
# Set your name
git config --global user.name "Your Name"

# Set your email (use the same email as your GitHub account)
git config --global user.email "you@example.com"

# View all config
git config --list

# Set VS Code as default editor
git config --global core.editor "code --wait"
```

> Always use **double quotes** for values containing spaces.

## 4. Key Terminology

| Term | Meaning |
|------|---------|
| **Repository (Repo)** | A folder tracked by Git. Just a fancy name for a folder. |
| **Working Directory** | Your local project folder where you edit files |
| **Staging Area** | A holding area — files you've marked to be committed next |
| **Commit** | A saved snapshot/checkpoint of your staged changes |
| **Branch** | An alternate timeline of development |
| **HEAD** | A pointer to your current branch's latest commit |
| **Remote** | A version of your repo hosted online (e.g., on GitHub) |
| **Origin** | The default name given to the remote repository URL |
| **Clone** | A copy of a remote repository downloaded locally |
| **Push** | Sending local commits to the remote repository |
| **Pull / Fetch** | Downloading changes from remote to local |
| **Merge** | Combining changes from one branch into another |
| **Rebase** | Rewriting the base of a branch onto a new starting point |

## 5. Git Internals — Behind the Scenes

> ⚠️ This section is for understanding — you'll rarely use these commands directly. But knowing them makes you a better engineer.

### Two Types of Git Commands

| Type | Description | Examples |
|------|-------------|---------|
| **Porcelain Commands** | High-level, user-friendly | `git add`, `git commit`, `git log` |
| **Plumbing (Gardening) Commands** | Low-level, internal | `git hash-object`, `git update-index`, `git write-tree` |

### Git's Internal Storage — The Three Musketeers

Git stores everything as **objects** in the `.git/objects` folder:

```
Commit Object
    └── Tree Object
            └── Blob Object (actual file content)
```

#### 1. Blob Object
- Stores the **actual file content**
- Binary Large Object

#### 2. Tree Object
- Stores **file structure** (names, modes, hashes of blobs)
- Like a directory listing

#### 3. Commit Object
Contains:
- Reference to a **Tree Object**
- **Parent commit** hash (empty for first commit)
- **Author** name & email
- **Committer** name & email
- **Commit message**

### SHA (Hash) IDs
Every object in Git gets a **unique SHA-1 hash** (40 characters). This hash is computed from the file's content, so identical content always gets the same hash.

### Inspecting Internals

```bash
# View contents of a commit object
git cat-file -p <commit-hash>

# View the tree referenced by a commit
git cat-file -p <tree-hash>

# View a blob (file content at a point in time)
git cat-file -p <blob-hash>
```

### Low-Level Workflow (Plumbing)
Here's what `git add` actually does behind the scenes:

```bash
# 1. Generate a hash for the file content
A1=$(git hash-object -w filename.txt)

# 2. Update the index (staging area) manually
git update-index --add --cacheinfo 100644 $A1 filename.txt

# 3. Write a tree object
TREE=$(git write-tree)

# 4. Create a commit object
COMMIT=$(echo "Initial commit" | git commit-tree $TREE)

# 5. Update the HEAD reference
git update-ref HEAD $COMMIT
```

This is what `git add` + `git commit` does automatically. Now you understand why those two commands are so powerful.

## 6. Core Git Workflow

```
Write Code → git add → Staging Area → git commit → Local Repo → git push → Remote (GitHub)
```

### Step-by-step

```bash
# 1. Initialize a repository
git status          # Always check first!
git init            # Creates a hidden .git folder

# 2. Add files to staging
git add filename.txt        # Add a specific file
git add file1 file2         # Add multiple files
git add .                   # Add ALL changed files

# 3. Commit staged files
git commit -m "Your commit message"

# 4. View history
git log
git log --oneline           # Compact view
```

### The `.git` Hidden Folder
When you run `git init`, a `.git` folder is created:

```
.git/
├── HEAD          ← Points to current branch
├── config        ← Repo-level configuration
├── description
├── hooks/        ← Scripts that run on Git events
├── info/
├── objects/      ← All commit, tree, blob data
└── refs/
    └── heads/    ← Branch pointers
        └── master (or main)
```

### Atomic Commits
Git recommends **atomic commits** — one logical unit of work per commit.

- ✅ "Add footer component"
- ✅ "Fix login bug"
- ❌ "Changed a bunch of stuff"

> The smaller and more focused your commits, the easier it is to go back to a specific point.

### Commit Message Style
Industry convention: **Present tense, imperative mood**

```
✅ Add footer to homepage
✅ Fix user authentication bug
✅ Update README with installation steps

❌ Added footer
❌ Fixed bug
❌ Updating readme
```

## 7. Git Commands Reference

### Checking Status & History

```bash
git status                  # What's staged, modified, untracked?
git log                     # Full commit history
git log --oneline           # One line per commit
git log --oneline --graph   # Visual graph
```

### Staging & Committing

```bash
git add <file>              # Stage a file
git add .                   # Stage all changes
git rm --cached <file>      # Unstage a file (keep it in working dir)
git commit -m "message"     # Commit with inline message

```

### Configuration

```bash
git config --global user.name "Name"
git config --global user.email "email"
git config --global core.editor "code --wait"
git config --list
```

### .gitignore

Create a `.gitignore` file in your project root to exclude files from tracking:

```
# .gitignore examples
.env
node_modules/

*.jpg

Git doesn't track empty folders. To include an empty folder in your repo, add an empty file called `.gitkeep` inside it:

```bash

## 8. Branching

Branches are **alternate timelines** of development. Think of them like parallel universes — changes in one branch don't affect another until you merge them.

### HEAD
`HEAD` is a pointer that always points to the **tip of your current branch**. When you switch branches, HEAD moves with you.

```
main:     A → B → C (HEAD)
feature:      B → D → E (HEAD when on feature branch)
```

### Branch Commands

```bash
# List all branches (* = current)
git branch

# Create a new branch
git branch branch-name

# Switch to a branch
git switch branch-name
git checkout branch-name     # Older syntax, still works

# Create AND switch to a new branch
git switch -c new-branch-name
git checkout -b new-branch-name   # Older syntax

# Rename a branch
git branch -m old-name new-name

# Delete a branch
git branch -d branch-name

# Change default branch name globally
git config --global init.defaultBranch main
```

### Visualizing Branches

Install the **Git Graph** extension in VS Code to see a visual timeline of all branches and commits.

### Practical Branch Workflow

```bash
# Start on main
git switch main

# Create a feature branch
git switch -c dark-mode

# Do your work...
git add .
git commit -m "Add dark mode styles"

# Go back to main
git switch main

# Files from dark-mode branch are gone from view — that's normal!
```

## 9. Merging & Merge Conflicts

### Fast-Forward Merge
When the source branch has no new commits since the feature branch was created, Git simply moves the pointer forward.

```
Before:  main: A → B
         feature: A → B → C → D

After merge: main: A → B → C → D  (no merge commit needed)
```

```bash
# Be on the branch you want to merge INTO
git switch main

# Merge the feature branch into main
git merge feature-branch
```

### Non-Fast-Forward (True) Merge
When both branches have diverged (both have new commits), Git creates a **merge commit**.

```
Before:
  main:    A → B → C → E
  feature: A → B → D → F

After merge:
  main:    A → B → C → E → M (M = merge commit)
                       ↑
                   D → F
```

This creates an extra commit (M) just for merging — some teams dislike this clutter.

### Merge Conflicts
A conflict occurs when **both branches modified the same part of the same file**.

```bash
git switch main
git merge feature-branch
# ⚠️ CONFLICT (content): Merge conflict in file.txt
```

#### Conflict Markers in File
```
<<<<<<< HEAD (current branch — what you have)
2024 is coming
=======
2025 is coming
>>>>>>> feature-branch (incoming changes)
```

#### Resolving in VS Code
VS Code gives you clickable options:
- **Accept Current Change** — keep your version
- **Accept Incoming Change** — take their version
- **Accept Both Changes** — keep both
- **Compare Changes** — view side by side

After resolving:
```bash
git add resolved-file.txt
git commit -m "Resolve merge conflict"
```

#### Abort a Merge
```bash
git merge --abort    # Undo the merge attempt entirely
```

## 10. Git Diff

`git diff` is an **informational command** — it shows differences between versions. It doesn't change anything.

```bash
# Show unstaged changes (working dir vs last commit)
git diff

# Show staged changes (staging area vs last commit)
git diff --staged

# Compare two branches
git diff branch1..branch2

# Compare two commits
git diff abc123..def456

# Compare specific files between commits
git diff abc123 def456 -- filename.txt
```

### Reading Diff Output

```diff
--- a/file.txt    ← "a" version (older/reference)
+++ b/file.txt    ← "b" version (newer)
@@ -1,4 +1,6 @@  ← line numbers
 unchanged line
-removed line     ← exists in "a" but not "b"
+added line       ← exists in "b" but not "a"
 another unchanged line
```

> ⚠️ `---` does NOT mean the file was deleted. `+++` does NOT mean the file was added. These are just **labels** for the two versions being compared.

## 11. Git Stash

Stash is a **temporary storage area** for uncommitted changes. Use it when you need to switch branches but aren't ready to commit.

```bash
# Save current changes to stash
git stash

# Save with a descriptive name
git stash save "work in progress on login"

# List all stashed entries
git stash list
# stash@{0}: WIP on main: abc1234 Latest commit
# stash@{1}: On feature: def5678 Another stash

# Apply the most recent stash (keeps it in stash)
git stash apply

# Apply a specific stash
git stash apply stash@{1}

# Apply AND remove from stash (most common)
git stash pop

# Delete a specific stash
git stash drop stash@{0}

# Clear all stashes
git stash clear
```

### Typical Stash Workflow

```bash
# Working on feature-branch, urgent bug reported!
git stash              # Save WIP

git switch hotfix      # Go fix the bug
# ... fix the bug ...
git add . && git commit -m "Fix critical bug"

git switch feature-branch
git stash pop          # Restore your WIP
```

## 12. Git Tags

Tags are **named labels** attached to specific commits — like sticky notes. Commonly used to mark release versions.

```bash
# Create a lightweight tag
git tag v1.0

# Create an annotated tag (recommended for releases)
git tag -a v1.0 -m "Release version 1.0"

# Tag a specific commit
git tag v1.0 <commit-hash>

# List all tags
git tag

# Push tags to remote
git push origin v1.0        # Push a single tag
git push origin --tags      # Push all tags

# Delete a tag locally
git tag -d v1.0

# Delete a tag on remote
git push origin --delete v1.0
```

> 💡 Most teams only tag **major releases**, not every commit. Tagging is usually done by release managers, not individual developers.

## 13. Git Rebase

Rebase **moves the starting point (base) of your branch** to a different commit — typically the latest commit on main.

> ⚠️ Rebase **rewrites history**. Use with caution. **Never rebase shared/public branches** (main, master, develop).

### Why Rebase?

**Problem with Merge:**
```
main:    A → B → C → E
feature:           D → F → M (M = unnecessary merge commit)
```

**With Rebase:**
```
main:    A → B → C → E
feature:               D' → F'  (no merge commit, clean history)
```

### How to Rebase

```bash
# Always be on your feature branch
git switch feature-branch

# Rebase onto main (get main's latest changes without a merge commit)
git rebase main
```

### Interactive Rebase
Squash, reorder, or edit multiple commits:

```bash
git rebase -i HEAD~3    # Interactively rebase the last 3 commits
```

### Conflict During Rebase

Conflicts are handled the same as merge conflicts:

```bash
# After resolving conflicts in the file:
git add resolved-file.txt
git rebase --continue    # Continue rebase

# Or abort entirely
git rebase --abort
```

### Rebase Rules
- ✅ Rebase your **local feature branch** onto main
- ❌ Never rebase `main` or any shared branch

## 14. Git Reflog

Reflog is a **complete history log** of everything that has happened in your repo — including checkouts, resets, merges, and rebases.

```bash
# View full reflog
git reflog

# View reflog for a specific branch
git reflog show main
```

### Use Case: Recovering Lost Commits

```bash
# Find the commit you want to return to
git reflog

# Reset to that commit (DESTRUCTIVE — can't undo easily!)
git reset --hard <commit-hash>

# Or using HEAD notation (go back N commits)
git reset --hard HEAD~2    # Go back 2 commits
```

> 💡 `git reflog` is your safety net. Even after a bad reset or rebase, reflog can help you recover lost work.

## 16. SSH Keys

GitHub **no longer allows username/password** for command-line operations. You must use **SSH keys**.

SSH works by generating a **public/private key pair**:
- **Private key** → stays on your machine (never share)
- **Public key** → uploaded to GitHub

When you push, GitHub verifies your identity by matching the keys.

### Generate SSH Key

```bash
# Generate a new SSH key (use your GitHub email)
ssh-keygen -t ed25519 -C "you@example.com"

# When prompted for file location, press Enter for default
# When prompted for passphrase, press Enter to skip (or set one)
```

### Add SSH Key to ssh-agent (Mac)

```bash
eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

### Copy Public Key

```bash
# Mac
cat ~/.ssh/id_ed25519.pub | pbcopy

# Windows (Git Bash)
cat ~/.ssh/id_ed25519.pub | clip

# Linux
cat ~/.ssh/id_ed25519.pub
```

### Add to GitHub
1. Go to **GitHub → Settings → SSH and GPG Keys**
2. Click **"New SSH Key"**
3. Give it a title (e.g., "My Laptop")
4. Paste your public key
5. Click **"Add SSH Key"**

### Test Connection

```bash
ssh -T git@github.com
# Hi username! You've successfully authenticated...
```

## 17. Pushing to GitHub

### Connect Local Repo to GitHub

```bash
# Check existing remote connections
git remote -v

# Add a remote (use the SSH URL from GitHub)
git remote add origin git@github.com:username/repo-name.git

# Verify it was added
git remote -v
# origin  git@github.com:username/repo-name.git (fetch)
# origin  git@github.com:username/repo-name.git (push)
```

### Push Your Code

```bash
# First push — set upstream
git push -u origin main

# All subsequent pushes (after upstream is set)
git push
```

### What `-u` Does
`-u` sets the **upstream** — it links your local branch to the remote branch. After this, just `git push` is enough.

### Pull from Remote

```bash
git pull                    # Fetch + merge
git fetch                   # Fetch only (doesn't merge)
git pull origin main        # Explicit pull from main
```

### Clone a Repository

```bash
git clone git@github.com:username/repo-name.git
```

Cloning automatically:
- Downloads all code
- Sets up `origin` remote
- Checks out the default branch

### README.md
GitHub automatically renders a `README.md` file on the repo homepage. Always include one!

```markdown
# Project Name

## Description
What does this project do?

## Installation
```bash
npm install
```

## Usage
How to use it.
```

## 18. Open Source Contribution

### What is Open Source?
Open source projects are public repositories where anyone can view, use, and contribute to the code.

### ⚠️ Important Warnings
- Don't contribute just for "profile building" with low-value changes
- README/grammar fixes are okay but aren't impressive as a developer
- Your contributions represent not just you, but your community
- Spammy PRs hurt the maintainers and your reputation

### The Right Way to Contribute

#### Step 1: Communicate First
- Read the `README.md` and `CONTRIBUTING.md`
- Find an issue you can genuinely fix or a feature you can add
- **Comment on the issue or open a discussion first** — ask if you can work on it
- Don't send code before communicating

#### Step 2: Fork the Repository
```
Original Repo (owner's)
        ↓ Fork
Your Copy on GitHub (username/repo-name)
        ↓ Clone
Your Local Machine
```

```bash
# Click "Fork" on GitHub, then clone YOUR fork
git clone git@github.com:your-username/forked-repo.git
cd forked-repo
```

#### Step 3: Set Up Remotes

```bash
# Your fork = origin (already set by clone)
git remote -v

# Add original repo as "upstream"
git remote add upstream git@github.com:original-owner/repo.git
git remote -v
```

#### Step 4: Create a Branch

```bash
git switch -c feature/my-contribution
```

#### Step 5: Make Your Changes

Write meaningful code, not trivial fixes. Test your changes.

```bash
git add .
git commit -m "Add feature: describe what you did clearly"
git push origin feature/my-contribution
```

#### Step 6: Open a Pull Request (PR)

On GitHub:
1. Go to your fork
2. Click **"Contribute → Open Pull Request"**
3. Write a **detailed PR description**:
   - What problem does this solve?
   - How did you solve it?
   - Screenshots/tests if applicable
4. Submit

#### Step 7: Respond to Feedback

Maintainers may request changes. Respond professionally and update your code.

### Keep Your Fork Updated

```bash
# Get latest changes from original repo
git fetch upstream

# Merge into your local main
git switch main
git merge upstream/main

# Push updated main to your fork
git push origin main
```

### Good vs Bad Contributions

| ✅ Good | ❌ Bad |
|--------|-------|
| Fix a real bug | "Fix typo" in README (as a beginner profile boost) |
| Add a useful feature | Randomly add whitespace |
| Improve performance | Open issues for things that aren't bugs |
| Write tests | Copy code from other projects |
| Improve docs with accurate info | Submit without communicating |
